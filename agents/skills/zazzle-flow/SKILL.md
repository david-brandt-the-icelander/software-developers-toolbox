# zazzle flow and zazzle review

## Leave to zazzle
- Spend your effort on the change. Do not format, lint, run builds, tests or coverage, write or update documentation, changelogs, commit messages or pull request text, or wait for CI yourself: zazzle's tools and its local agent do those after you.
- Do not judge coverage or style by reading code; read the receipt `verify` and `tidy` give.

## Before
- `zazzle flow preview` shows what applies: checks, the branch pull requests target and its review level, the effects delivery may have, and conflicts in the repository's guidance. Settle a conflict with the user before delivering.
- Delivery needs the repository to opt in with `.zazzle/flow.json` (`zazzle flow init` prints a starter; `--write` saves it). Verify and review work without it.

## Orchestrator
- By default the local model does zazzle's own work (writer, lint fixer, test author, conflict resolver, CI triager, review briefs). `--orchestrator claude:MODEL|codex:MODEL [--orchestrator-effort E]` on any `zazzle flow` or `zazzle review` command, `agents.orchestrator` in `.zazzle/flow.json`, or `ZAZZLE_ORCHESTRATOR` / `ZAZZLE_ORCHESTRATOR_EFFORT` gives that work to an external model instead; reports show its tokens apart from the execution agents' (reviewers, final reviewer, fix agent). Use it only when the user asks or the policy sets it: it costs tokens and sends the diff to that model.

## Verify
- `zazzle flow verify` runs the repository's own checks that apply to the change. The receipt names the tree it ran on; a changed tree has no receipt until you verify again.
- A missing program, a skip or a check that does not apply is listed, never counted as a pass. Logs are cited by path; read them only for a failure.

## Tidy
- `zazzle flow tidy` runs the formatters' and linters' fix commands (`format` and `lint` checks; discovered for Cargo, Go, .NET and npm), checks again, and gives lint that still needs an edit to the local agent. What is left after that is yours.

## Coverage
- `zazzle flow coverage` runs the `coverage` checks, reads their report (lcov, Cobertura, a Go profile, coverage.py JSON or llvm-cov missing lines) and lists the changed files' uncovered lines and partial branches with tests to model on. Read that instead of judging coverage yourself.
- `--author AGENT --tests PATH` has a cheap agent write tests for the gaps; they stay only if every coverage check still passes. Check that their assertions match the behavior you want.

## Dependencies and the branch
- `zazzle flow audit` runs the dependency audits (cargo-audit, npm audit, govulncheck, pip-audit, dotnet's vulnerable list) when a manifest or lockfile changed (`--all` for every one) and lists the advisories; `--fix` runs a fix command where one exists. Choosing to upgrade or replace a dependency is yours.
- `zazzle flow deps [--branch NAME]` updates dependencies with the package managers (cargo update, npm update, go get -u=patch, poetry update): major bumps are reviewed by the strongest agent, the audits and checks run, and the update is committed with a message listing the bumps only when everything passes; otherwise it is put back. Do not edit lockfiles or bump versions yourself.
- Generated code and license headers are tools' work: `zazzle flow generate` reruns the generators whose inputs changed (`--check` reports stale outputs), `zazzle flow headers --fix` adds missing license headers (`tidy` does too). Never edit a generator's outputs by hand: change its inputs.
- Merging is zazzle's: do not merge branches or pull requests yourself. `zazzle flow merge` merges the pull request when the policy allows `merge`, its checks are green on the head and no review finding is open.
- `zazzle flow update` merges the target branch in: conflicted lockfiles are regenerated by the package manager, other conflicts go to the local agent, a complex merge (conflicts the local agent resolved, three or more files changed on both sides, or a security or compatibility boundary) is reviewed by the strongest agent first, and the merge is committed only when no marker is left, the review finds no problem and the checks pass; otherwise it is aborted and the conflicts are listed for you. It never rebases or forces; `--push` pushes the result.

## Write
- `zazzle flow write docs --intent 'TEXT'` has the cheap writer update the READMEs and `.dev` records beside and above the changed files (add `--paths` for others); JSON stays valid and the repository's `docs.check` commands must pass, or its changes are put back.
- You decide the intent and the compatibility decision; the writer only phrases them: `zazzle flow write pr --intent 'TEXT' --compat 'none: no client sees a change'`.
- `changelog --apply` adds the entry under Unreleased; commit it with the change it describes. `commit` and `pr` with `--apply` save the draft for `deliver`.
- A draft that says `MISSING:` or fails validation comes back with exit 1: supply the fact and run it again.

## Deliver
- `zazzle flow deliver --paths P.. -m 'MESSAGE' --pr --draft [--body-file F] [--require-verified]`: only the named paths are committed. Running it again after a partial failure reuses the commit, the push and the open pull request.
- A remote with commits the branch lacks is reported, never forced: fetch and merge, then deliver again.
- `zazzle flow ci` waits for the pull request's checks on its current head and reports once. Do not poll yourself. A failed job's log comes back cut to its errors and triaged by the local model (`FAILURE job | test | path:line | cause`, `OWNER`, `NEXT`): act on that, and read the full log only if the triage is unsure.

## Test first
- Settle the behavior, the test paths and a nearby reference test first: `zazzle flow test-first --behavior 'TEXT' --tests PATH --reference FILE --run 'CMD' --expect 'TEXT'`.
- A test is accepted only when it fails for the stated reason. The fixer changes production code only; if it says the assertion is wrong, that decision is yours.

## Review
- `zazzle review --into BRANCH --intent 'TEXT'` reviews at that branch's level (feature, development, staging, production; default: this branch's). Earlier levels are brief because each later merge gets a stricter pass.
- It fixes confirmed findings, re-verifies and re-reviews before reporting. Documentation findings go to the cheap writer, code findings to the fixer, and the formatter runs after each fix. What is left is a decision for the user, missing access, or blocked verification. Use `--read-only` for findings without edits.
- `--bench` reports each phase with what went to hosted agents (charged) and what ran locally.
